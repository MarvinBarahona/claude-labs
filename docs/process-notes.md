# Process Notes

Append-only log of suggestions the drafting/build process can't apply itself: coding-convention/process changes, and changes to files it doesn't own (`README.md`, `CLAUDE.md`, other skills). Written during planning or graduation, never applied automatically. Reviewed and cleared manually, on your own schedule.

- **`vision-lab`** — when a plan parallelizes frontend/backend build tracks and the frontend reuses Messages Console's streaming shape, watch for a "helpful" simplification that merges the non-streaming and streaming-turn-complete apply paths into one shared method without explicitly threading `streamEvents` through: Messages Console keeps two separate call sites for setting the inspector's call state, and Vision Lab shares one `applyEnvelope` method but takes `streamEvents` as an explicit optional parameter — both preserve the field. Live Tool-Use Console and Document Research Assistant already merged onto one shared apply method that doesn't thread it through, so for those two labs the inspector panel silently loses the raw stream-event log the moment `turn_complete` lands. Caught by the E2E spec here, not by frontend unit tests; worth calling out explicitly in a future build brief for a streaming lab, and worth a separate look at whether the two silently-dropping labs should be fixed to match or left as-is.
- **`extended-thinking-bench`** — `backend/src/testing/anthropic/message-builders.ts` has no shared `fakeThinkingMessage()` helper; this feature builds a thinking+text fake message locally in its own spec files instead (`fakeTextMessage(answerText, { content: [...] })`). It's the only consumer of `thinking` content blocks so far — worth promoting to a shared helper in `test-doubles.md` once a second lab actually needs one.
- **`agent-playground-tool-result-caps`** — a cached API-usage reference consulted during
  planning/building can be stale, or its prose can be misread even when the underlying source
  is accurate: an MCP toolset's per-tool restriction shape (`configs`, keyed by tool name) was
  first implemented from a cached summary in a shape the real Messages API rejected outright.
  Worth a live-docs check (not just the cached reference) before shipping any request-payload
  change that hasn't yet been exercised against the real API — especially one involving a nested
  or keyed-object shape, where "per-item overrides" can be misread as an array when the real
  shape is an object.
- **`frontend/tsconfig.json`** — TypeScript `strict` mode (and Angular's `strictTemplates`) isn't enabled; only four piecemeal flags (`noImplicitOverride`, `noPropertyAccessFromIndexSignature`, `noImplicitReturns`, `noFallthroughCasesInSwitch`) are set, none of which cover `strictNullChecks`, `noImplicitAny`, or `strictPropertyInitialization`. The frontend is already written as if strict were on (readonly everywhere, `unknown` + manual runtime narrowing, explicit `| null` unions), so turning it on would likely need few or no code changes — but it's a repo-wide config edit outside any single lab's build scope, worth doing as its own deliberate compile-and-fix pass rather than folded into an unrelated feature's work. Found during a full frontend code review; not caught by any existing test, since `npm test`'s type-checking is separate from this config gap.
- **`document-research-assistant-large-file-warning`** — the repo's `no-multiline-comments` hook check runs against a touched file's *entire* contents, not just the diff: editing `backend/test/document-research-assistant.e2e-spec.ts` tripped it on a pre-existing, unrelated two-line `//` comment above the files-api-reuse assertion. Had to condense that comment to one line just to get this task's own edit to land. Worth a standalone pass over other long-lived spec/source files for the same latent violation, so an unrelated future edit doesn't hit the same surprise.
